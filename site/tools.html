BSO cluster

Draws everything around one business service offering: its service, the service instances it depends on, their tech offerings and dynamic CI groups, and each instance's service map.

Download .js Source ↗

How to run it

  1. On your instance, open System Definition › Scripts - Background, in the global scope.
  2. Paste the script and set ROOT at the top to the offering's number (e.g. 'SO0001234') or sys_id.
  3. Select Run script.
  4. Open the link it prints. The editor shows the diagram, ready to adjust and export.

What it prints

  • csdmflow source, to paste into the editor or save as a .csdm file.
  • An editor link that opens the diagram directly. It's compressed, so it stays short enough to paste into a chat or a ticket.
  • The data as JSON on one line (the csdm-graph format), for other tools.

Safe to run

It only reads: plain queries, no inserts, updates or deletes. Group members are counted per class, not read one by one, so even large groups stay quick.

Every box links back to its record on your instance: a click on a service or group opens its form, a stack of CIs or a member count opens the list of those CIs. Opening a record still needs a login.

The diagram travels in the link after the #, which browsers never send to a server. The names, your instance's address and the records' sys_ids can still be read by anyone who has the link.

Settings

ROOTThe business service offering to start from: its number or sys_id. A tech offering is refused with a note saying so.
LAYOUTcross, tiers, row or lanes; empty for the default. You can also switch it in the editor.
MAX_CI_DEPTHHow many hops a service map is followed below its instance. Default 5.
DEBUGtrue also prints the offering's relationships and every link left out, with the reason. Useful when something you expect is missing.

What it walks

From the offering: its business service and portfolio, the service instances it depends on, their applications, tech offerings and dynamic CI groups, the tech offerings' services and groups, the groups' members, and each instance's service map, downwards. Other offerings of the same service are left out, so the picture stays about this one offering.

BSO transport

Lists what to move to carry the modelling around business service offerings to another instance: a filtered list per table to export as XML, the order to import them in, and the steps to do by hand on each service instance.

Download .js Source ↗

How to run it

  1. On the source instance, open System Definition › Scripts - Background, in the global scope.
  2. Paste the script and fill in SERVICES with the business services and the offerings of each to transport (see Settings). Set TARGET_INSTANCE to the target's instance name.
  3. Select Run script.
  4. Open each list it prints, right-click a column header and select Export › XML.
  5. On the target, import the files in the order printed (right-click a column header in any list › Import XML), do the manual steps on each service instance, then import the relationships last.

What it prints

  • One link per table, in import order: cmdb_group, cmdb_group_contains_encoded_query, cmdb_ci_query_based_service, the service instances per class (cmdb_ci_service_discovered, …) and cmdb_rel_ci. Each opens the list filtered to those records by sys_id. A table with nothing to export gets no link.
  • For each service instance, a link to it on the target and the dynamic CI groups to add with the Manual population method, one Add Method per group.
  • Warnings for anything the lists leave out, such as a group that also uses saved queries.

Safe to run

It only reads: plain queries, no inserts, updates or deletes. Exporting and importing is left to you.

Settings

SERVICESAn array of business services, each with a name, a number and its offerings, each with a name and a number: 
[
  { "name": "Email", "number": "BSN0001001", "offerings": [
    { "name": "Email Standard", "number": "SO0001234" },
    { "name": "Email Premium", "number": "SO0001235" }
  ] }
]
The names are there to read; the numbers decide. A warning says when a name differs from the instance's, or an offering isn't one of its service's. Tech offerings and unknown ones are left out with a warning.
TARGET_INSTANCEThe target's instance name (e.g. acmeprod), for the links in the manual steps. Empty links to the source instance. The export lists always open on the source.

What it collects

From the offerings: the service instances they depend on, the dynamic CI groups that populate them (related to them or on their maps), the CMDB groups behind those and their encoded queries. It exports the relationships offering → instance and tech offering Contains instance or group.

An instance's own relationships to its groups are left out: they belong to its population, which the platform rebuilds when you add the groups by hand. Importing them as XML would skip the business rules that keep a service's map together.

The offerings and tech offerings themselves aren't exported: they must already exist on the target, with the same sys_ids.
